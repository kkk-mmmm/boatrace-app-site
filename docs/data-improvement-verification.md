# 履歴改善と運用検証

履歴更新は毎日、日本時間02:10のGitHub Actionsで前日までの365日を再集計する。スケジュールには遅延があり、公式アーカイブが未提供なら不完全な履歴へ切り替えず停止する。

承認済み係数・標準化・温度・過去検証結果を日次更新で変更しない。係数の再学習候補は日本時間の暦月ごとに初めて成功した実行で1回作り、`models/monthly-candidates/YYYY-MM/`にモデル・検証結果・ハッシュ・レビュー待ち状態を保存する。同月の再実行はハッシュを確認してスキップする。失敗した学習は再試行可能。候補の本番採用は別のレビュー・リリースとする。初回導入月は導入後の初回実行が対象。開発用の年次履歴ワークフローも日次の再集計だけとし、コード変更時の自動再学習をしない。

## 追加集計

- 直近30・90日の選手全体／枠別成績。1着率・着順点・ST平均／標準偏差・スタート順位と、それぞれの標本数を保持する。
- 実際の進入コース別履歴。枠番で代用しない。今回の参照コースが展示進入であること、本番進入は未確定であることをデータに明記する。
- 開催日・区分別のST平均だけでなく標準偏差・件数を保持する。
- 展示ST→本番STの照合で、本人確認できた展示進入・本番進入を区別して保存する。古い記録に進入がなければ推定で埋めない。
- 展示STは直近7完了日の取得漏れを新しい日から補完し、1実行最大300レース、1秒以上のページ間隔を守る。照合済みレースを再取得しない。保留件数・失敗を`models/exhibition-st/last-update.json`に記録する。300件は保証された成功件数ではなく取得試行上限。

追加情報は`annualHistory.lanes[].data_details`に入り、承認済み14特徴量には追加しない。履歴の重みを変えず、候補モデル比較のための入力を先に整備する。モデル全体IDは日次の履歴更新で変わるが、`coefficient_id`は同じ係数・標準化・温度なら一定である。

## 保存と照合

公開用リポジトリの`verification-data`専用ブランチを永続の検証保存先とし、Pagesの配信対象に含めない。既存の予想と結果を上書きしない。GitHubキャッシュだけを保存先にしない。公開情報から作る記録で、認証情報やユーザーの実際の購入履歴は含めない。

- 5分間隔を目安とする既存のPagesデータ取得に続いて記録する。公式への追加取得はしない。1分ごとの全履歴を保証する仕組みではない。
- 締切10〜3分前に収集処理が受信できた予想・オッズ・入力を`RECEIPT_BEFORE_CUTOFF`として保存する。
- Workerが保持する締切3分前以前の保存提案を後で取得したものは`WORKER_REPORTED_ONLY`として別集計する。事後受信を事前受信と呼ばない。
- 同一レース・同一群の複数記録は最新の保存予想1件だけを評価し、元記録は削除しない。保存時刻・モデル・入力・確率・オッズをハッシュで検証する。
- 翌日、既に取得した公式結果アーカイブのハッシュを確認して再解析し、選手・着順・本番STと公式3連単払戻を別保存する。解析キャッシュだけを正解として信用しない。結果の追加ネット取得は不要。
- 各10点・各100円の固定条件で、確率上位と期待値上位の的中率・回収率を分けて集計する。払戻が照合できないときは回収率を計算せず、オッズから払戻を推定しない。
- 確率帯別の推定確率と実的中頻度、対数損失、Brier誤差、展示STと本番STの差・補正誤差を集計する。正常な6艇レースが対象。当日・未来、未照合、選手変更、欠場やF/Lなどは評価へ混ぜず、理由を記録する。

レポートは専用ブランチの`reports/current.json`。各予想の全120通りは不変の`snapshots/`、公式結果は`results/`に残す。集計開始前の過去成績を運用実績に遡って追加しない。蓄積直後の件数ではモデルの改善・収益性を断定しない。

ブランチの容量は保存レース数に比例して増える。日次監視で保管容量を確認し、長期運用では不変の月次アーカイブへの移管を検討する。保持期間を決めずに過去記録を自動削除する処理は入れていない。
