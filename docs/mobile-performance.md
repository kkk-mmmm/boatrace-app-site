# スマホ表示の比較測定と初期読込改善（v1.41.0）

改善前b0e732dの公開ビルドと、同一の保存データをコピーして対象のJS/CSS/HTMLだけ変更した版を比較しました。ローカルHTTP、Chrome CDP、390×844px、CPU4倍、下り1.6Mbps・遅延150ms・キャッシュ無効、各URL2回。対象はトップ、場別（大村）、条件別検証、期待値記事です。空レースの保存版と過去の検証記録を使用し、開催中の全場・最新オッズを測ったものではありません。

| URL | 平均LCP（前→後） | 観測CLS（前→後） |
| --- | --- | --- |
| トップ | 2094→2054ms | 0.2521→0.0190 |
| 大村 | 2236→2210ms | 0.2127→0.0012 |
| 条件別検証 | 836→832ms | 0→0 |
| 期待値記事 | 840→860ms | 0→0 |

表示時間はほぼ同程度で、少数試行の差から改善を断定しません。初期の空レース表示では、厳選レース・締切一覧に領域を確保したことで大きな位置ずれが減りました。開催中に複数のカードが増えるケースや外部API障害の全ケースで同じCLSになるとは主張しません。新しい初期領域は厳選110px・締切一覧66pxの最低高で、情報が多い場合は通常通り伸長します。

Chart.jsは評価・自信度タブが表示されるまで取得せず、既存の版・SRI・CSPを維持。取得Promiseを共有して重複を抑制し、レースやキャンバスが変わった後の遅い応答では旧データを描画しません。CDN障害でも数値表を残し、15秒ごとの画面更新で取得を連発しません。グラフ取得が始まるまでの数値表・切替は利用できます。

旧15件検証のarchive.json（未圧縮約360KB）も検証企画を開いた時だけ取得。初期画面でarchive.jsonを要求せず、初回の検証表示で取得することをブラウザテストで確認しました。企画・記事データの日別取得や最新オッズの取得頻度は変更していません。

測定前はChart.jsの外部リクエストがこの環境の証明書検証で失敗しています。正常なCDN取得時の転送・解析コストの削減量はこの結果から推定できません。また改善前のarchive.jsonは観測打切り時に転送中であり、ログのencoded_bytesは完全な総通信量ではありません。CLS/FCP/LCPもこのナビゲーションの観測値で、実ユーザーの75パーセンタイルやPageSpeedスコアではありません。INPは測定していません。

条件別検証はこの保存版で約1.4MBのJSONを読み込みます。実配信の圧縮転送量は未確認で、今後の実測結果によって日別取得・集計形式の軽量化を検討します。今回、記録の切捨てや集計条件の変更は行いません。

比較の生データはmobile-performance-lab.json。再測定コマンド（ChromeをCDP 9222で起動しローカルサーバーを準備）：

```
node tools/site/measure_performance.mjs http://127.0.0.1:4173/ /tmp/performance.json
```

新しい測定ツールはページを前面化し、可視状態と未完了リクエストURLも記録します。データ取得待ちが残る場合は完全な転送量とみなさないでください。本番の実ユーザー速度・外部通信・Lighthouseスコアの確認は別途必要です。
